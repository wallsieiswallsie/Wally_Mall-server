# Implementation report

1. **Client requirements:** transactional marketplace discovery, favorites, seller onboarding/catalog, addresses, variant cart, multi-seller checkout, payment/order timelines, in-app notifications, operational moderation, finance/staff/fee/audit management. Actual client implementation and transaction-prototype documentation took precedence over obsolete discovery-only docs.
2. **Original migration baseline:** ten ESM migrations and README, now located at `database/migrations/`. No original package, Knex config, seed system, connection utility or server application existed. The database module and migration subdirectory were subsequently given responsibility-based names; migration filenames and contents remain unchanged.
3. **Migrations used:** original `001_identity.js` through `010_finance.js`, in dependency order. Added one module-local Knex configuration and CLI; no duplicate migration tree or initial migration.
4. **ERD/schema:** executable migrations are available. The referenced Wally_Mall.sql/ERD is missing; parity remains unverified, with no replacement ERD generated.
5. **Client-to-database mapping:** documented in [client-api-mapping.md](client-api-mapping.md), including UUID/variant conversion and removal of direct browser payment outcomes.
6. **Architecture:** Fastify HTTP/validation/security/domain code in `src/`; Knex connections, repositories, locks and transactions in the authoritative database module.
7. **API modules:** auth, users, addresses, categories, stores, products, search, favorites, cart/quote, checkouts, orders, payments, seller, admin, super-admin, reports and notifications.
8. **Authentication:** salted scrypt passwords; rotating hashed refresh sessions; signed expiring access credentials; database-backed logout/revocation.
9. **Authorization:** live unrevoked role resolution; strict request schemas; buyer ownership; member capability checks; server allowlist response projections; authenticated status enforcement.
10. **Seller/store ownership:** applications/documents precede approval; approval grants seller role and draft store ownership through store_members. Location is supplied after approval; activation requires a primary address.
11. **Product/variant model:** product metadata, explicit variants with authoritative price, product_media, tags/product_tags and inventory per variant. New listings await moderation.
12. **Inventory:** `on_hand - reserved`; stable row-lock order; atomic reserve/release/sale movements. Initial service supports default-location inventory only.
13. **Multi-seller checkout:** one checkout, one order per store, item/address/fee snapshots, histories, fulfillments and pending payment intent committed together. Late failures roll everything back.
14. **Payments:** provider boundary plus development-only mock; signed raw-body webhook; amount/currency validation; provider-event uniqueness; inventory/order reconciliation and expiry runner. Late success events needing manual reconciliation are retained with no processed_at and do not commit a sale.
15. **Fulfillment:** seller-only valid next transitions, per-store membership, separate fulfillment state and history. No invented courier/tracking/pickup values.
16. **Admin/Super Admin:** operational Admin has masked, nonfinancial views. Super Admin controls buyer access, admin provisioning/reset/revocation, financial snapshots, fees, refunds and audit retrieval.
17. **Audit/moderation:** reports and moderation_actions; server-generated actor/request context; sensitive writes append audit_logs; existing append-only triggers tested.
18. **Search:** existing relational fields, tags and DB synonyms, centralized visibility, bounded filters/pagination, real search/view records, actual review aggregates. No new search schema or extensions.
19. **Database gaps:** editable platform settings; preapproval application location; multi-location inventory traceability. [Gap report](database-gap-report.md) contains evidence and proposals only; schema remains frozen.
20. **Files added:** package/lockfile, .gitignore, .env.example, README; `src/{app,config,domain,security,validation,payment,index,expire}.js`; database module `index.js`, `knexfile.js`, `cli.js`, repositories `{identity,catalog,accounts,management}.js`, transactions `{commerce,payments}.js`, seed `001_development.js`; unit/integration/startup tests; documentation files in `docs/`. Existing client and migration files were not changed.
21. **Tests actually run:** 20 passing tests with PostgreSQL, including concurrency, transaction rollback, authorization and actual HTTP startup. See [verification](verification.md).
22. **Migration commands run:** `npm.cmd run db:latest`, `npm.cmd run db:status`; tests also execute complete rollback/reapply using Knex's migration API. The development seed command was executed with generated test credentials.
23. **Start command:** `npm.cmd --prefix server start`, after installing dependencies, configuring `server/.env` and migrating the selected application database. Verified entrypoint: `node src/index.js` through the real-process startup test.
24. **Remaining boundaries:** real payment/refund provider and reconciliation, storage ownership/private document access, notification delivery beyond in-app, identity verification/recovery, invitation delivery, production deployment/TLS/distributed limits, scheduled expiry execution, large-scale search/reporting performance, and connecting the unchanged client to the API. Mock production startup is intentionally refused. No real settlement/payout or promotion workflow is invented.

The server is implemented and verified for its documented development/provider boundaries. The unavailable ERD/SQL and real-provider requirements prevent claiming a fully verified production deployment.
